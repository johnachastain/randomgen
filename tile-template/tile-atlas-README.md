# Tile Atlas — Reskin Authoring Guide

How to size and produce a PNG reskin set for the bitmask dungeon tiles.

## TL;DR

- **Author every tile at 128 px per cell.** Single-cell tiles = **128 × 128 px**, square (H = W).
- **PNG-32 with alpha** (overlay/trim tiles are transparent; base tiles are opaque).
- **Multi-cell tiles** scale by their cell count at the same 128 px/cell (see the table below).
- Keep the **same slot names** as the current SVG set — the renderer swaps art by filename, no code change.

## Why 128 × 128

| What | Value |
|---|---|
| On-screen size of one base cell | **32 CSS px** (`S = 32` in `src/lab/geomorph-dungeon/Page.tsx`) |
| Tile shape | **Square** — a base tile covers exactly one grid cell (1:1) |
| Detail sub-grid | `SUB = 4` → finest trim feature ≈ `S/4` = 8 logical px |

A base cell renders at 32 CSS px. Author at an integer (power-of-two) multiple of 32 so scaling stays clean and the art is crisp on HiDPI displays and when zoomed:

| Scale | Pixel size (H × W) | Use |
|---|---|---|
| 1× | 32 × 32 | Don't author here — soft/blurry on any HiDPI display |
| 2× | 64 × 64 | Bare minimum for a Retina display |
| **4×** | **128 × 128** | **Recommended** — crisp on Retina, headroom for zoom, modest file size |
| 8× | 256 × 256 | Only for deep-zoom / future-proofing; ~4× the file weight |

On a 2× (Retina) display a 32 px cell already paints to ~64 device px. Authoring at 128 gives 2× oversampling even at 100% zoom, so it stays sharp as the map is zoomed in. At 128 px/cell, the finest trim feature (8 logical px) gets a full 32 px of art — plenty of detail.

## Per-slot dimensions

Pick **one** px-per-cell value for the whole set (128 recommended) and multiply by each slot's cell footprint. The atlas JSON encodes each slot's footprint as its `viewBox` in **100 units per cell** (divide by 100 to get cell count).

| Slot type | Cells | viewBox (current SVG) | PNG @ 128 px/cell | Count |
|---|---|---|---|---|
| Single-cell (floor, wall, water, door, trim, pillar, stairs, portals, corner bites/arcs, rr-corner/trim, sm alcoves…) | 1 × 1 | `100 × 100` | **128 × 128** | 85 |
| Large alcove — N / S | 3 × 2 | `300 × 200` | **384 × 256** | 4 |
| Large alcove — E / W | 2 × 3 | `200 × 300` | **256 × 384** | 4 |

*(93 slots total. Names/footprints are enumerated in `tile-atlas.json`.)*

## Authoring rules

1. **One px-per-cell for the whole set** — mixing resolutions breaks alignment. 128 is the recommended constant.
2. **Base tiles are square 1:1** (floor / wall / water / door — one cell each).
3. **Seamless edges** on the tiling base layers (floor, water): art must wrap cell-to-cell with no interior padding, so repeated cells have no visible seam.
4. **Alpha / transparency** on the overlay trim tiles (wall lips, arcs, corner bites, alcove bites): the art must align exactly to the cell edges so the overlay lines up with the base layer beneath it.
5. **Keep the slot names** identical to the current `public/dungeonTiles/*.svg` filenames (PNG extension is fine — the renderer swaps art by name).

## Notes / gotchas

- **Base floor / wall / water and active doors are currently `<div>` color fills, not image tiles.** To reskin those with textures they must first be rendered as `<img>` tiles (tracked in the roadmap as the R2/R4 base-layer-as-tiles work). The trim/detail/feature slots above are already `<img>`-based.
- **This atlas is the interchange contract.** `tile-atlas.png` (labeled contact sheet) + `tile-atlas.json` (slot names + native geometry + layout rects) define the required slot set. Any producer (hand-painted PNGs, image-ingest, AI) should conform to it, then go through validate → slice → themed manifest. The atlas's own `cellPx` / `scale` describe the *contact-sheet* rendering, not the authoring target — author to the **128 px/cell** guidance above.
