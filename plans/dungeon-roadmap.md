# Dungeon geomorph — roadmap & backlog

Canonical roadmap for the two-layer bitmask dungeon (`src/lab/geomorph-dungeon/`, route `/refactor/geomorph-dungeon` — route unchanged; **relocated 2026-07-09** from `refactorGeomorphs/` into the `lab/` zone) and the shared-core work it seeds. Durable design/rationale lives in [`architecture.md`](./architecture.md).

> **North star:** the map is the **visual view of a config-driven random-object engine** — the project's arc is *random naming → config-driven objects (weighted/tagged values, cross-property influence, nesting, parent→child tags) → the map as their rendered representation*. See [`vision.md`](./vision.md). On this roadmap, **Idea 10 (room profiles)** is step 1 onto the map, and the **Config-object engine → map as its view** epic (below) is the destination.

## Backlog

### Epic — Config-object engine → map as its view *(cross-cutting north star)*
The long-horizon destination ([`vision.md`](./vision.md)): the map becomes the **visual view of a config-driven random-object engine**. The engine is **already ~70% prototyped** — weighted/tagged value pools + strategy selection (`names/`), a flat config-object with cross-property influence (`configCharacterGen/`), and a nested config-object tree with parent→child influence + single-property re-roll (`configDungeonGen/` — `Config<T>` + `ItemRecord{type,id,parentId,properties}`). **The work:** (1) **unify** those three into one core engine — `core/config` (schema + registry + ordered updater-runner), `core/text` (tracery-lite), `core/rng` (seeded), `core/model` (object/tag types), retiring the divergent copies (two `character/functions`, tuple-vs-registry config, jotai-only-in-dungeon); (2) **model the map's rooms/levels/dungeon as `ItemRecord`s** in that tree; (3) **make the bitmask map render the object tree** — geometry is one facet, the generated semantic object is the source of truth, and naming/descriptions/props all read from it. **Idea 10 = step 1** (room-as-object on the map). Pairs with **T1** (seed the whole tree → reproducible) + **Zod** (the config schema, `architecture.md` §2). Proceeds via promotion discipline (`architecture.md` §1); long-horizon, not a single sprint. **Design in progress:** [`generation-engine.md`](./generation-engine.md) (content & selection model — the A–F target + the "capability regressed" review); the concrete sub-tasks land here once that doc finalizes.

### Generation features
- **E6 / Idea 6 — Download JSON** — "Download JSON" button; `DungeonResult` is already serialisable. Export `{version, cols, rows, S, SUB, materialLegend, ...dungeon}` via Blob + `<a download>`. Follow-ups: import/load + seeded repro. *Small.*
- **Idea 4 / E4 — Symmetrical zones** — mirror room+corridor *structure* across H/V/both axes with a jitter knob; decoration runs free. MVP whole-map → sub-zones. Optional: mirror elevation. *Medium→large.*
- **Idea 7 — Underground caves** — organic CA / drunkard's-walk carve, meandering tunnels, underground rivers (a meandering `Material.Water` channel); no doors/pillars v1; needs a connectivity flood-fill guarantee. Whole-map mode first. Reuse `geomorph-ca`/`geomorph-walk`. *Medium→large.*
- **Idea 8 — Pre-defined room patterns** — a `RoomPattern` registry (size/shape + feature specs + "magnets" = named anchor points for elements & connectors); apply a pattern to a room instead of the procedural passes. **8a — pattern-editor page:** a standalone route where the user clicks cells → assigns features/magnets → saves records into a *shared pattern collection* other pages read. *Large.*
- **Idea 3c — curve-aware trim polish** / more materials (lava, second wall type) / richer base generation. *Various.*
- **Phase B2 — flush MAIN rooms** — needs a `passable()` connectivity refactor (edge-aware flood over walls/edge-walls). *Medium.*
- **Stairs — literal equal tile counts** (deferred) — elevation is consistent by *net level change* today; making two connections between the same rooms use the same *number* of stair tiles is a distinct, harder constraint.

#### Idea 10 — Room profiles (semantic properties → seed naming, descriptions & props) *(foundational milestone)*
**✅ Derivation + naming shipped 2026-07-10** — `RoomInfo.profile` is populated and **profile-aware naming** consumes it (see Shipped). `type` is feature-derived for now (no cave/temple signal until Idea 7). **Remaining consumers:** real descriptions, prop weighting. **Scope note:** profiles are **rooms-only** today → non-room elements (halls/connectors/stairs/portals) get their own profiles in **Idea 12**.
Today the room data model is a **hybrid**: `RoomInfo` centralizes geometry, but room *content* (water, pillars, doors, elevation) is decentralized across parallel grids and `roomAt` (cell→room) isn't even exported — so "is this room a flooded cave?" must be derived by scanning the footprint (see [`architecture.md` §4](./architecture.md#4-room-profile--semantic-properties-seed-naming--descriptions--props)). This milestone adds a **post-generation pass** (runs *after* water/pillars/doors/elevation, where `roomAt` + all grids are live) that derives a centralized **`RoomProfile`** per room and attaches it to `RoomInfo`. Fields: **`type`** (cave/masonry/temple/crypt/… — the primary naming seed, via a small classifier) + `material`, `size`, `water`, `pillared`, `shape`, `elevation`, `connectors`, `features`. The profile becomes the **single seed** for **context-aware naming** (`core/naming` `roomName(profile, rng)` — cave rooms get cave names), **real room descriptions** (`src/lab/room-description` reads the profile, not random PoC values), and **prop placement** (Idea 9 weights by `type`); later it feeds the config Dungeon-CONTENT generator. Derive it in the dungeon *feature*; keep `core/naming` + the text engine generic (they take tags, not grids). Pairs with **T1** so profile→name→description is reproducible. **This is step 1 of the config-object → map integration** (see the epic below + [`vision.md`](./vision.md)) — the room becomes a config-driven object whose properties are rule-generated, exactly like `configDungeonGen` already does at the data level. *Med; unblocks the naming/description quality work.*

#### Idea 9 — Props, fixtures & interactables *(major milestone)*
A *dungeon-dressing* pass: furniture, fixtures & hazards placed into generated rooms/corridors. **Shared new infra (build FIRST):** a **props layer** on `DungeonResult` — `props: Prop[]`, `Prop = { c, r, kind, facing?, footprint? }` (a sparse list, like `portals[]`); a placement pass in `dungeon.ts` (reuse the `isWall`/`isFloor`/`rectAllWall` free-cell + margin logic from the apse/alcove/side-room passes) seeds props on valid cells; each kind renders as an `<img>` overlay in `Page.tsx` (fractional-cell CSS position/size → **sub-cell footprints need no grid change**); art via a new emit block in `scripts/generateDungeonTiles.ts` (same pattern as `door_*`/`pillar`/`stairs_*`) exposed through new `tileConfig.ts` constants; a per-kind visibility toggle in the ⚙ flyout. **Scope caveat:** "interactable" = *visual placement + data* for v1 (like room names/numbers — a static render); real interaction (trip a trap, pull a lever, open a chest) needs a game-loop/inspector layer that doesn't exist yet → **deferred**. Every subtask needs **new tile art**.
- **9a — Portcullis** *(door variant)* — extends the **EDGE/door layer** (not props): add a door *style* to `EDGE.door` (a parallel door-style map, or a `kind` on the door edge) so a doorway can render as a portcullis (vertical bars) instead of a leaf. New `portcullis_{n,s,e,w}` tiles (like `DOOR_TILES`); render in `Page.tsx`'s door pass. *Small–med.*
- **9b — Levers** *(wall-mounted interactable)* — props layer; anchored to a **wall face** of a floor cell (sub-cell, offset to the wall edge, `facing`). New `lever_*` art. *Small.*
- **9c — Traps** *(1-cell floor hazard)* — props layer; a marker on a **Floor** cell (pressure plate / spikes / rune); optional `armed`/`type` field for future logic. New `trap_*` art. *Small.*
- **9d — Dais** *(raised/lowered platform)* — extends the **elevation/stairs layer** (not props): a small platform (1 cell or N×N) inside a room, ringed by a trim of stair tiles (step up/down on open sides). Reuses `StairGrid`/`LevelGrid` + new dais step/corner-trim art. Heaviest (local geometry + ring trim + level bookkeeping). *Med.*
- **9e — Altars** *(½×1 furniture)* — props layer; a sub-cell rectangular table surface (half-cell footprint), often centred / against a wall. New `altar` art. *Small.*
- **9f — Sarcophagi** *(½×1 box)* — props layer; a sub-cell coffin/box footprint. New `sarcophagus` art. *Small.*
- **9g — Chests** *(small box, treasure)* — props layer; a small footprint, often against walls / in rooms; optional `contents` flag → future hook into the **config Dungeon-CONTENT generator** + room descriptions (loot). New `chest` art. *Small.*
- **Suggested order:** props-layer infra + one simple furniture prop (9g/9e) → rest of the furniture cluster (9e/9f/9g) → levers/traps (9b/9c) → portcullis (9a, edge layer) → dais (9d, elevation layer, heaviest).
- **Cross-ref:** once **Idea 10 (room profiles)** lands, placement can weight by room `type` (altars/sarcophagi favor temple/crypt rooms, etc.) instead of placing uniformly.

#### Idea 11 — Editable config objects (seed + overrides) *(future; engine capability)*
An object starts fully random from a **seed** (T1); a future UI lets the user override individual property values (buttons/dropdowns) + per-field **lock** / **re-roll**. Persisted & shareable state = **`(seed, overrides)`** — a *sparse* `path → value (+lock)` map, not a full copy; the object is a pure function `resolve(seed, overrides)`. **Requires per-property sub-seeding** — each property's rng derives from `hash(seed, path)` (a `core/rng` `subRng()`), so editing/re-rolling one field never scrambles the rest (avoids "seed drift" from a single linear stream). Overrides act as **forced inputs** so dependent properties re-derive (cross-property influence, parent→child tags), while sub-seeding keeps unrelated fields stable. This upgrades `configDungeonGen`'s existing single-property mutation hook (`rerollProperty`/`updateProperty`, currently store-mutation / freeze+patch) to the reproducible model. Determinism/override design detail in [`generation-engine.md`](./generation-engine.md) §6. Pairs with the **Config-object engine** epic (above) + Idea 10. *Med–large.*

#### Idea 12 — Map-element profiles (halls · connectors · stairs · portals) *(future; extends Idea 10)*
Idea 10 gives **rooms** a `RoomProfile`; the **non-room** elements deserve their own profiles too. The generator already builds this structure internally then discards it: **halls/corridors** = `allEdges`/`chosen` (`CEdge = {ai, bi, path[]}` — knows both room endpoints + cells); **staircases** = `runs` + `runDelta` (a run with `runDelta ≠ 0` is a staircase); **connectors/doors** = `EDGE.door` edges (only *counted* per-room today); **portals** = `portals: Portal[]` (a discrete list already, but no profile). So the dungeon is *already* a graph of rooms + corridors + runs + stairs + portals flattened to grids at the end — this extension = **stop discarding it; expose every element as a first-class object with a profile.** That's the vision/engine "map = view of a nested element tree" made concrete → converges with the **Config-object engine** epic (elements become `ItemRecord`s). **Design:** a unified element model `{ id, kind, …geometry, profile }`, `kind ∈ room|hall|connector|stair|portal`, rolled out **incrementally** (keep `rooms[]`+`RoomProfile`; add non-room elements+profiles; converge on one `elements[]` / id-keyed registry). Per-kind sketches: **HallProfile** (length/width/turns/water/`connects[a,b]`/levelChange → passage/tunnel/gallery/flooded-channel); **StairProfile** (direction from `runDelta` sign/steps/levelDelta/connects → stair/flight/spiral); **ConnectorProfile** (style: door now, portcullis/archway = Idea 9a; `joins[a,b]`; orientation; locked? → door/gate/threshold); **PortalProfile** (entrance/exit, edge side, up-out/down-deeper, dest level). **Enabling work:** expose the internal graph (`chosen`/`runs`/`runDelta`/`portals`) on `DungeonResult` + a small **door-extraction** pass (the only new segmentation) — this **subsumes T2** (below). Feeds naming/descriptions/props for *all* elements; makes **Idea 11** stronger (every element addressable by id). *Note:* disambiguate `RoomProfile.connectors` (a room's ways-out **count**) from a **connector element** (a door object). *Med–large.*

### Tile theming pipeline (R) — the ATLAS is the shared contract
See [`architecture.md`](./architecture.md) for the full pipeline. `tile-template/tile-atlas.{png,json}` (atlas-builder, done) is a tileset **interchange format** (93 slot names + geometry + layout). Pipeline: *any tile source → atlas (conforming to JSON) → validate → slice → themed manifest.*
- **R1 — Image-driven reskin** *(producer)* — analyze an example image → retune `generateDungeonTiles.ts` palette/line-style (recommended start), or AI paint into the labeled atlas canvas. *Small→large.*
- **R2 — PNG/Photoshop path** *(producer)* — PNG support near-free (tiles are `<img src>`; manifest → `.png`). Atlas → hand-paint → slice → themed manifest. Needs a **slicer**. Caveat: base floor/wall + doors are `<div>`s (would need converting to `<img>` tiles to texture). *Tooling small–med.*
- **R3 — Runtime skin selector (UI)** *(consumer)* — a "Skin" dropdown swaps the active theme live. `Skin = {id,label,tileBase,tileExt,palette,…}`; derive tile URLs by name from the active skin instead of fixed `tileConfig.ts` constants; base fills/grid from `skin.palette`. Frozen v1–v4 untouched. *Refactor small–med.*
- **R4 — Tile variants (variation families)** — a slot can hold K art options picked per cell (straight wall trims, floor, water). Contract extends to families (`<slot>__<i>` + `variantCount`/`weights`). Deterministic per-cell pick (positional hash → stored index once T1 lands). Floor/water must become tile families first. *Small–med + base-layer-as-tiles.*
