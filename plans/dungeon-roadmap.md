# Dungeon geomorph — roadmap & backlog

Canonical roadmap for the two-layer bitmask dungeon (`src/lab/geomorph-dungeon/`, route `/refactor/geomorph-dungeon` — route unchanged; **relocated 2026-07-09** from `refactorGeomorphs/` into the `lab/` zone) and the shared-core work it seeds. Durable design/rationale lives in [`architecture.md`](./architecture.md).

> **North star:** the map is the **visual view of a config-driven random-object engine** — the project's arc is *random naming → config-driven objects (weighted/tagged values, cross-property influence, nesting, parent→child tags) → the map as their rendered representation*. See [`vision.md`](./vision.md). On this roadmap, **Idea 10 (room profiles)** is step 1 onto the map, and the **Config-object engine → map as its view** epic (below) is the destination.

## Backlog

### Epic — Config-object engine → map as its view *(cross-cutting north star)*
The long-horizon destination ([`vision.md`](./vision.md)): the map becomes the **visual view of a config-driven random-object engine**. The engine is **already ~70% prototyped** — weighted/tagged value pools + strategy selection (`names/`), a flat config-object with cross-property influence (`configCharacterGen/`), and a nested config-object tree with parent→child influence + single-property re-roll (`configDungeonGen/` — `Config<T>` + `ItemRecord{type,id,parentId,properties}`). **The work:** (1) **unify** those three into one core engine — `core/config` (schema + registry + ordered updater-runner), `core/text` (tracery-lite), `core/rng` (seeded), `core/model` (object/tag types), retiring the divergent copies (two `character/functions`, tuple-vs-registry config, jotai-only-in-dungeon); (2) **model the map's rooms/levels/dungeon as `ItemRecord`s** in that tree; (3) **make the bitmask map render the object tree** — geometry is one facet, the generated semantic object is the source of truth, and naming/descriptions/props all read from it. **Idea 10 = step 1** (room-as-object on the map). Pairs with **T1** (seed the whole tree → reproducible) + **Zod** (the config schema, `architecture.md` §2). Proceeds via promotion discipline (`architecture.md` §1); long-horizon, not a single sprint. **Design in progress:** [`generation-engine.md`](./generation-engine.md) (content & selection model — the A–F target + the "capability regressed" review); the concrete sub-tasks land here once that doc finalizes.

> **Progress (2026-07-13).** The engine primitives are built in `core/` (`rng, model, select, text, config, naming`), and the **map's tree is now config-objects on that engine**: Dungeon (root, generated `type`+`name`) → Rooms (`roomObject`) → Elements (`elementObject`), each an `ItemRecord`. **All five vision mechanics now run on the real map**, incl. the last two: **cross-property influence** (dungeon `name` reads its `type`) and **parent→child tag inheritance** (dungeon `type` mood-colors children — see Shipped). **Still open (the big rocks):** (1) render map **geometry** *from* the object tree — today the tree is a semantic overlay (names/descriptions read from it) but geometry is generated separately; (2) **unify the legacy generators** (`names/`, `configCharacterGen/`, `configDungeonGen/`) into the core engine + **Zod** schema, retiring the divergent copies; (3) **editable objects** (Idea 11: `seed + overrides`, per-property `subRng`); (4) converge `rooms[]`+`elements[]` into one id-keyed tree.

#### Idea 10 — Room profiles (semantic properties → seed naming, descriptions & props) *(foundational milestone)*
**✅ Derivation + naming shipped 2026-07-10** — `RoomInfo.profile` is populated and **profile-aware naming** consumes it (see Shipped). `type` is feature-derived for now (no cave/temple signal until Idea 7). **Remaining consumers:** real descriptions, prop weighting. **Scope note:** profiles are **rooms-only** today → non-room elements (halls/connectors/stairs/portals) get their own profiles in **Idea 12**.
Today the room data model is a **hybrid**: `RoomInfo` centralizes geometry, but room *content* (water, pillars, doors, elevation) is decentralized across parallel grids and `roomAt` (cell→room) isn't even exported — so "is this room a flooded cave?" must be derived by scanning the footprint (see [`architecture.md` §4](./architecture.md#4-room-profile--semantic-properties-seed-naming--descriptions--props)). This milestone adds a **post-generation pass** (runs *after* water/pillars/doors/elevation, where `roomAt` + all grids are live) that derives a centralized **`RoomProfile`** per room and attaches it to `RoomInfo`. Fields: **`type`** (cave/masonry/temple/crypt/… — the primary naming seed, via a small classifier) + `material`, `size`, `water`, `pillared`, `shape`, `elevation`, `connectors`, `features`. The profile becomes the **single seed** for **context-aware naming** (`core/naming` `roomName(profile, rng)` — cave rooms get cave names), **real room descriptions** (`src/lab/room-description` reads the profile, not random PoC values), and **prop placement** (Idea 9 weights by `type`); later it feeds the config Dungeon-CONTENT generator. Derive it in the dungeon *feature*; keep `core/naming` + the text engine generic (they take tags, not grids). Pairs with **T1** so profile→name→description is reproducible. **This is step 1 of the config-object → map integration** (see the epic below + [`vision.md`](./vision.md)) — the room becomes a config-driven object whose properties are rule-generated, exactly like `configDungeonGen` already does at the data level. *Med; unblocks the naming/description quality work.*

#### Idea 9 — Props layer: placement · rendering · tile-art infra *(infrastructure milestone; the delivery mechanism for Idea 14's content types)*
> **Reconciled 2026-07-13:** this is now the **INFRA** (the *how* — placement, rendering, tile art) that lands **Idea 14's content/interactable TYPES** on the map. **Idea 14 is the single source of truth for the type/config-object/state model** (the *what*). The old per-type subtasks (9a–9g) moved into the **Idea 14 catalog**; what remains here is the shared delivery layer + the placement-layer routing.

A *dungeon-dressing* pass that places generated room-children into rooms/corridors. **Shared infra (build FIRST — unblocks Idea 14):** a **props layer** on `DungeonResult` — `props: Prop[]`, `Prop = { c, r, typeId, state?, facing?, footprint? }` (a sparse list, like `portals[]`; `typeId` → an Idea 14 registered type, `state` → its interactable state); a placement pass in `dungeon.ts` (reuse the `isWall`/`isFloor`/`rectAllWall` free-cell + margin logic from the apse/alcove/side-room passes) seeds items on valid cells **weighted by room profile/type** (Idea 10); each renders as an `<img>` overlay in `Page.tsx` (fractional-cell CSS pos/size → **sub-cell footprints need no grid change**), with **per-state tile variants**; art via a new emit block in `scripts/generateDungeonTiles.ts` (same pattern as `door_*`/`pillar`/`stairs_*`) through new `tileConfig.ts` constants; per-kind visibility toggles in the ⚙ flyout. **Interaction** (open/toggle/trip/unlock) now lives in the **Play / interaction layer** — no longer deferred. Every type needs **new tile art**.
- **Placement-layer routing** *(the infra distinction; the TYPES + states are defined in the **Idea 14 catalog**):*
  - **Props layer** (sub-cell `<img>` overlays) — furnishings (furniture sub-types, altars, sarcophagi), chests, levers, traps.
  - **Edge/door layer** (extend `EDGE.door` with a *style*, like `DOOR_TILES`) — door variants: double doors, portcullis.
  - **Elevation/stairs layer** (reuse `StairGrid`/`LevelGrid`) — dais (a **raised OR lowered platform, reached by a few steps up/down** — a small localized elevation change within a room), ladder (vertical shaft). *(Add these as room-feature TYPES in the Idea 14 catalog.)*
- **Suggested order:** props-layer infra + one simple furnishing (chest/altar) → the furniture/furnishing cluster → levers/traps (+ the interactable state machine from the Play layer) → door-style variants (portcullis / double doors, edge layer) → dais/ladder (elevation layer, heaviest).
- **Cross-ref:** placement weights by room `type` (Idea 10); the type/state/config-object model + the full item list = **Idea 14**; runtime interaction = the **Play / interaction layer**.

#### Idea 11 — Editable config objects (seed + overrides) *(future; engine capability)*
An object starts fully random from a **seed** (T1); a future UI lets the user override individual property values (buttons/dropdowns) + per-field **lock** / **re-roll**. Persisted & shareable state = **`(seed, overrides)`** — a *sparse* `path → value (+lock)` map, not a full copy; the object is a pure function `resolve(seed, overrides)`. **Requires per-property sub-seeding** — each property's rng derives from `hash(seed, path)` (a `core/rng` `subRng()`), so editing/re-rolling one field never scrambles the rest (avoids "seed drift" from a single linear stream). Overrides act as **forced inputs** so dependent properties re-derive (cross-property influence, parent→child tags), while sub-seeding keeps unrelated fields stable. This upgrades `configDungeonGen`'s existing single-property mutation hook (`rerollProperty`/`updateProperty`, currently store-mutation / freeze+patch) to the reproducible model. Determinism/override design detail in [`generation-engine.md`](./generation-engine.md) §6. Pairs with the **Config-object engine** epic (above) + Idea 10. *Med–large.*

#### Idea 12 — Map-element profiles (halls · connectors · stairs · portals) *(✅ Shipped 2026-07-13, uncommitted — see Shipped)*
**Delivered:** `DungeonResult.elements: MapElement[]` (hall/stair/connector/portal), each with a typed `profile` + per-kind number + config-object name + `core/text` description; UI pills (halls/stairs/portals) + generalized inspector. Rooms stay in `rooms[]` for now. **Remaining follow-ups:** converge `rooms[]` into the unified `elements[]` tree; feed profiles into prop placement (Idea 9); implement the now-unblocked **T2** invariant. Original design note below. —
Idea 10 gives **rooms** a `RoomProfile`; the **non-room** elements deserve their own profiles too. The generator already builds this structure internally then discards it: **halls/corridors** = `allEdges`/`chosen` (`CEdge = {ai, bi, path[]}` — knows both room endpoints + cells); **staircases** = `runs` + `runDelta` (a run with `runDelta ≠ 0` is a staircase); **connectors/doors** = `EDGE.door` edges (only *counted* per-room today); **portals** = `portals: Portal[]` (a discrete list already, but no profile). So the dungeon is *already* a graph of rooms + corridors + runs + stairs + portals flattened to grids at the end — this extension = **stop discarding it; expose every element as a first-class object with a profile.** That's the vision/engine "map = view of a nested element tree" made concrete → converges with the **Config-object engine** epic (elements become `ItemRecord`s). **Design:** a unified element model `{ id, kind, …geometry, profile }`, `kind ∈ room|hall|connector|stair|portal`, rolled out **incrementally** (keep `rooms[]`+`RoomProfile`; add non-room elements+profiles; converge on one `elements[]` / id-keyed registry). Per-kind sketches: **HallProfile** (length/width/turns/water/`connects[a,b]`/levelChange → passage/tunnel/gallery/flooded-channel); **StairProfile** (direction from `runDelta` sign/steps/levelDelta/connects → stair/flight/spiral); **ConnectorProfile** (style: door now, portcullis/archway/double = door-style variants, see Idea 14 catalog + Idea 9 edge-layer; `joins[a,b]`; orientation; locked? → door/gate/threshold); **PortalProfile** (entrance/exit, edge side, up-out/down-deeper, dest level). **Enabling work:** expose the internal graph (`chosen`/`runs`/`runDelta`/`portals`) on `DungeonResult` + a small **door-extraction** pass (the only new segmentation) — this **subsumes T2** (below). Feeds naming/descriptions/props for *all* elements; makes **Idea 11** stronger (every element addressable by id). *Note:* disambiguate `RoomProfile.connectors` (a room's ways-out **count**) from a **connector element** (a door object). *Med–large.*

#### Idea 13 — Dungeon floors (multi-level dungeons) *(major milestone; realizes the vision's `Dungeon → Level → Room` nesting layer)*
Extend the parent→child tree with a **Floor** layer between Dungeon and Room. A dungeon = the root object (name/type, ✅ shipped 2026-07-13) + a series of **numerically descending floors**, each its OWN map (`DungeonResult`) and its own config-object with a **name + type** that inherits from the dungeon and flows down into that floor's rooms/elements (extends the parent→child inheritance shipped 2026-07-13). A **UI floor selector** switches the viewed floor.
- **Terminology:** the new **floors** axis is distinct from `DungeonResult.levels` = per-cell **elevation/z within one map** (+ the `showLevels` toggle) — keep "levels/elevation" for z.
- **Portal line-up (the trick):** floor N's **exit** portals connect to floor N+1's **entrance** portals through a connecting staircase of a **standard fixed length**. **PoC = same-cell alignment** — the entrance on N+1 is placed at the SAME `(c,r)` as the exit on N (vertical drop; the standard-length flight drawn down on N, up on N+1), which requires **shared floor dimensions**. Generation runs **top→bottom**: floor 1's exits are placed freely, then each deeper floor's entrances are **constrained** to its parent's exit cells (a new input to portal placement — today entrances are chosen randomly + independently, `dungeon.ts` `placePortal`/`carvePortal`). Exit/entrance **counts reconcile by construction** (floor N exit count = floor N+1 entrance count); floor 1 carries the surface entrance, the bottom floor has no exits.
- **Blast-radius (why it's major):** **Data —** a new wrapper `DungeonComplex = { seed, name, type, floors: Floor[] }` (`Floor ≈ DungeonResult + { number, name, type }`); the single-map `DungeonResult` consumed by `Page.tsx`/`roomDescribe`/`elementDescribe`/JSON/tests becomes "a floor within a complex." **Generation —** a new `generateDungeonComplex(cols, rows, floorCount, seed?)` that sub-seeds each floor (`subRng(seed, path)`) and threads exit→entrance constraints downward; `generateDungeon` gains a "required entrance positions" param; each floor built as a config-object child (`floorObject.ts`, like `roomObject`/`dungeonObject`) so floor `type` inherits from the dungeon and into its rooms. **UI (`Page.tsx`) —** a **Floors count** control + a **floor selector** (tabs/±/dropdown); current-floor state; map/mini-map/inspector/header all operate on the selected floor; header shows dungeon name/type + floor #/name/type; JSON export = the whole complex. **Tests —** alignment invariant (each floor-N exit has a floor-N+1 entrance at the same cell; counts match) + whole-complex determinism per seed. **Untouched —** frozen snapshots v1–v5 (own copies); the single-map generator stays usable.
- **Planned extensions (each its own later roadmap item + planning):**
  - **13a — Inter-floor stair layer (connecting `StairRun`s)** *(design captured 2026-07-14; implement later — supersedes the old "offset-by-stair-run" note)*. **Problem:** the same-cell / soft-aligned PoC leaves the connection *logically vague* — a floor's exit and the next floor's entrance are two independent stairwell stubs that merely land near each other; **no staircase is actually modeled between them.** **Design:** an **interstitial layer between each floor pair `N↔N+1`** (same grid dimensions as the floors) holding the connecting staircases as **first-class `StairRun` objects**. A `StairRun` starts at floor N's **exit** cell, ends at floor N+1's **entrance** cell, and is a chain of straight **flights** joined by **landings** — the 90°/180° bends. **Rules:** stay in-bounds; when a flight would run off a map edge, drop a **landing** and bend; descend continuously so the whole run = exactly **one floor's** drop (the run's length gives the real "standard stair length" for free). **Endpoints stay soft-placed** (today's exit-varied / entrance-biased-near placement is the input); the run **adapts** to whatever offset by bending — a bigger offset just means a longer run / more landings.
    - **Model fit:** turns the two portal stubs into the **two endpoints of one object** → an **inter-floor connector element** (slots into the `StairProfile`/connector model, Idea 12); **unifies ladders** (Idea 14 catalog) as the degenerate `StairRun` with **zero horizontal length** (a pure vertical shaft).
    - **View options (all documented; START with the interstitial step):** (1) **Interstitial step in the floor selector** — the selector gains half-steps: `Floor 1 → [Stairs 1↔2] → Floor 2 → …`, giving each connecting run its own dedicated view/map between floors *(chosen first cut)*; (2) **overlay on adjacent floors** — draw each run's footprint on the two floors it joins (near the exit on N, near the entrance on N+1) so you trace it without a separate view; (3) **per-portal inspector** — click an exit/entrance portal → a panel shows its full staircase (flights + landings + level drop). *(1)–(3) are future variations of the same underlying `StairRun` data.*
    - **Blast-radius (later):** **Data —** a `StairRun[]` per floor-pair (on `DungeonComplex`, or between adjacent `Floor`s), each `{ from:{floor,c,r}, to:{floor,c,r}, flights:[…], landings:[…], levelDelta:-1 }`. **Generation —** a run-router: pathfind exit→entrance on the interstitial grid emitting flights + landings with the edge-bend rule; deterministic (sub-seeded). **UI —** the interstitial half-step in the selector + a stair-run renderer. **Untouched —** floor generation stays as-is; the runs are an additive layer over the existing endpoints.
  - **13b — Per-floor dimensions** — floors may differ in size; alignment then needs a shared anchor / coordinate mapping between floors.
- **Fit:** the concrete Level layer of the **Config-object engine → map as its view** epic ([`vision.md`](./vision.md) §5); pairs with **T1**/`subRng` (seed the whole complex) + the 2026-07-13 parent→child inheritance. *Large.*

#### Idea 14 — Room contents: occupants & furnishings (room-child config-objects) *(major; realizes the vision's `Room → Monster/Treasure` leaf layer)*
> **✅ Furnishings + Occupants PoCs + navigable inspector shipped 2026-07-14** (see Shipped) — the `core/config` registries + profile-weighted placement + mood-named items (furnishings + monster/NPC occupants with group counts) + generated descriptions + the navigable ref-stack inspector (cross-links + back) + labeled content markers (brown/purple `<roomNum><letter>` pills). Establishes the shared props/placement/marker infra. **Extensions to pick up later:** more registered types from the **type catalog** below (levers/traps/chests-with-state, furniture sub-types); **child objects (treasure/loot)** — the deferred nesting layer (a chest's treasure, a monster's loot as child config-objects; the inspector ref-stack is built to slot a future "treasure" inspectable); **real tile art** instead of pills (the **R** pipeline / Idea 9 art); **movement** (occupants → the play layer's `Entity`); **interactability + state** (open/closed/locked, lever↔target linking — the play layer's `Interactable`, keyed by id); creature-specific descriptor pools; and a flat **props list / region membership** exposed for the play layer.

A room gains **zero or more children**, each generated as a **config-object parented to the room** (extends `roomObject.ts`; the leaf of the `Dungeon → Level → Room → …` tree in [`vision.md`](./vision.md) §5, which `configDungeonGen` already prototypes at the data level). Two behavioral categories:
- **Occupants** — **movable** in Player mode; typically **monsters or NPCs**. Each occupant TYPE has its own config-object definition (its properties + child objects) + generation. → the play layer's **`Entity`** (the "other movable elements" the play-layer item anticipated).
- **Static room-children** — **not movable** in the PoC but often **interactable**; each TYPE has its own config-object model + generation. Covers **furnishings, interactable elements, and new room features**. → the play layer's **`Interactable`**, and **subsumes Idea 9's type list** (altars, sarcophagi, chests, levers, traps — the former 9a–9g — are registered furnishing/interactable TYPES here). **One source of truth:** types/config-objects/states live **here (Idea 14)**; the placement/render/tile-art delivery is **Idea 9** (reframed as infra); runtime interaction is the **Play / interaction layer**.
- **Model:** a **content type registry** (reuse `core/config` `createRegistry`) — each type registers a `Config<T>` (properties + rules) + its art; a room's generation rolls a **count + type mix weighted by the room's profile/type** (a crypt room → undead occupants + sarcophagi; a temple → altars) and places each on a footprint cell (Idea 9 props-layer placement). Each child carries `id` + `parentId=room`, so the play layer keys entity/interactable runtime state by child id, and **Idea 11** can edit each via `(seed, overrides)`.
- **Blast-radius:** **Data —** the room object gains `children` (e.g. `{ occupants: OccupantObject[], furnishings: FurnishingObject[] }` or a `RoomChild` union with a `category`); a **content registry** of type definitions; `DungeonResult`/room exposes them + cell placement. **Generation —** a per-room content pass (count/type weighted by profile; placement reusing Idea 9's free-cell logic; sub-seeded per child). **Rendering —** occupant + furnishing markers/tiles (Idea 9 art pipeline; occupants = new monster/NPC art). **Play —** occupants = movable entities, furnishings = interactables (the play-layer abstractions). **Untouched —** DM view shows all; generation stays deterministic; existing rooms/elements unaffected (additive).
- **Fit / convergence:** the **config Dungeon-CONTENT generator brought onto the map** — `configDungeonGen`'s Monster/Treasure tree grounded on the real dungeon; the concrete leaf of the **Config-object engine → map as its view** epic. Pairs with **Idea 13** (children live on a floor's rooms), the **Play / interaction layer** (movement + interaction), **Idea 9** (furnishing types), and **Idea 11** (editable children).
- **Type catalog (initial, non-exhaustive — user-provided).** Each becomes a registered type (config-object + states + art). Grouped by role:
  - **Connectors & door-likes** *(refine the connector element — Idea 12; delivered via the Idea 9 edge/door-style layer):*
    - **Door** — states **open / closed / locked** (adds `locked` to the play-layer PoC's open/closed); per-state tile variant.
    - **Double doors** — a door variant: **two leaves side by side** (a 2-wide doorway → needs a 2-wide opening at generation).
    - **Portcullis** — a door-like variant: **vertically sliding bars** at a standard doorway; starts **locked + interactable** (raise to open); a typical **lever target**.
    - **Ladder** — "stairs but a **vertical shaft**": a vertical-shaft connector. *(Open: same-floor elevation shaft vs inter-floor link, cf. Idea 13; a stair/portal variant.)*
    - **Secret door** *(user-added 2026-07-15)* — a **door variant** whose map marker is the letter **"S"** positioned where a door would sit. Can be **locked** (unlock via key / a linked **lever** — reuses the lever→target linking mechanic below) and can be **lever-opened**. **Hidden in Player mode until discovered** (clicked/searched) — a *hidden-until-found* interactable (see the Play-layer fog/reveal note); in DM mode it's always shown. Otherwise behaves like a normal door (open/closed/locked states + per-state tile variant). *Incremental.*
  - **Room interactables** *(room-children — Idea 14; placed via the Idea 9 props-layer):*
    - **Lever** — **links to one or more target interactables** (portcullis, traps, locked doors) → pulling it **unlocks and/or opens** them. Introduces the **linking / wiring** mechanic (a lever records `targets: interactableId[]` at generation).
    - **Trap** — a rectangular floor zone (typically **1 cell**); states **set / triggered / deactivated**; can be a lever target.
  - **Furnishings** *(room-children — Idea 14; placed via the Idea 9 props-layer):*
    - **Chest** — interactable furnishing; states **open / closed / locked**.
    - **Barrel** *(user-added 2026-07-15)* — a **container** furnishing (sibling of Chest); states **open / closed**; holds loot child-objects later (cf. the deferred treasure/loot nesting layer, Idea 14 extensions).
    - **Urn** *(user-added 2026-07-15)* — a **smaller container** furnishing; **breakable** as well as openable. Same registry pattern as Chest/Barrel.
    - *(**Sarcophagus** already shipped as a furnishing type — `furnishings.ts` — with a **crypt** placement weight; user note "often placed in niches/alcoves" = a **placement-affinity** refinement to fold into Idea 9 placement, cross-ref the new **Niches** geometry item.)*
    - **Furniture** — **non-interactable**, no states; a furnishing category with many **sub-types** (chairs, tables, beds, shelves, …) — decorative/placement only.
  - **Shared mechanics (the extensible backbone — live in the Play/interaction layer's `Interactable`):** (1) a generic **interactable state machine** — each type declares its **state set + transitions + per-state tile variant** (door open/closed/locked; portcullis locked/open; trap set/triggered/deactivated; chest open/closed/locked); (2) **`locked`** as a **cross-type state** with **unlock paths** — key / linked lever / (future) skill check; (3) **linking/wiring** — an interactable (lever now; pressure-plate / key later) **targets** other interactables to drive their state.
  - **Opens to resolve at implementation:** double-door 2-wide opening geometry; ladder placement (same-floor elevation vs inter-floor, cf. Idea 13); locked-door unlock path; lever→target cardinality + how links are generated (proximity / same-room / theme).
- *Large (framework med; each registered type incremental).*

### Play / interaction layer — DM ↔ Player Character modes *(major new axis; the deferred game-loop layer)*
A **mode toggle** switches between **Dungeon Master** (current behavior — everything visible) and **Player Character** (interactive play).
