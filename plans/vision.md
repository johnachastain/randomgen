# Project vision — a config-driven random-object engine; the map is its view

> The north star for this repo. Design mechanics live in [`architecture.md`](./architecture.md); the milestone backlog in [`dungeon-roadmap.md`](./dungeon-roadmap.md). This doc says **where the whole project is going** and why.

---

## 1. Origin story

1. **It started as a random name generator** — curated word lists + string templates producing lists of names.
2. **Wanting depth behind the names** led to the **config-driven refactors**: model data as **objects with defined properties**, where each property's value is **randomly generated by its own rule** (not one global randomizer).
3. **Five needs emerged**, and each is now a first-class concept:
   - **weighted** random results (some values more likely than others);
   - **tags on values** (values carry semantic labels);
   - **cross-property influence** — a generated property's value is *shared* to influence the random generation of *other* properties;
   - **nesting** — a config-driven object can **contain other config-driven objects**;
   - **parent → child tag inheritance** — tags flow down the containment tree to influence a child's generation.
4. The **Config Dungeon Generator** (`src/configDungeonGen/`) is the early prototype of the nested version (property set deliberately simplified).
5. **End state:** the **map is the visual representation** of these config-driven, randomly-generated (nested) data objects. The bitmask dungeon isn't the product — it's the *view* onto a generated object tree.

---

## 2. The engine model (the concepts)

The target is **one** generation engine expressed in these primitives:

1. **Config-driven object** — a schema of named properties. Precedent: `Config<T> = Record<prop, { required, updater }>` (`configDungeonGen/functions/generate.ts`).
2. **Per-property generation rule** (`updater`) — each property has its own generator. Generation is **ordered** so a later property can read earlier ones.
3. **Weighted, tagged value pools** — `TaggedItem = [value, tags[], weight]` (`shared/types.ts`); selection is a weighted, tag-filtered pick (`filterTaggedList`). Strategy-level weighting via `WeightedVariantFilter = [number, VariantFilter]`.
4. **Cross-property influence** — a generated value becomes a **tag** that filters another property's pool (same object).
5. **Nesting / composition** — objects contain objects: `ItemRecord = { type, id, parentId, properties }` forms a tree (Dungeon → Level → Room → Monster/Treasure).
6. **Parent → child tag inheritance** — a child's generation reads parent context/tags (e.g. a Level's `type` steers its Rooms).
7. **Determinism / seeding** — one seedable RNG so an entire object tree is reproducible (roadmap **T1**).
8. **Schema + validation** — **Zod** as the single source of truth for a config's TS type *and* runtime validation of user-edited configs (see `architecture.md` §2).

## 3. Current state — the vision is already ~70% prototyped

The primitives exist today, split across three places (this is what "unify into core" means):

| Prototype | What it proves | Key code |
|---|---|---|
| **`names/`** | Weighted + **tagged** value pools; weighted **strategy** selection; tag-filtered picks | `TaggedItem`, `WeightedVariantFilter` (`shared/types.ts`); `filterTaggedList`, `weightedVariants`, `getTwoWordName`/`getAlliterativeName`/`getTagSetName` (`names/functions.ts`) |
| **`configCharacterGen/`** | **Flat** config-object: ordered per-property rules; **cross-property influence** | `characterConfigTuple` = `[prop, updater, …]`; `socialClass` → tag → filters `title`/`occupation`; `gender` → tag → `firstName` (`character/config.ts`) |
| **`configDungeonGen/`** | **Nested** config-objects; **parent → child influence**; single-property re-roll | `Config<T>` + `ItemRecord{type,id,parentId,properties}`; `roomNameUpdater` reads parent `level.properties.type` → type-appropriate room names; `updateProperty(id,key)` + `configRegistry` (`functions/generate.ts`, `basic.ts`, `state.ts`) |

**Divergence to reconcile:** there are two copies of the tag engine (`character/functions`), two config shapes (tuple vs registry), and `jotai` state only in the dungeon prototype. The vision unifies these into one engine.

## 4. The gap — the map isn't in the system yet

The **bitmask MAP generator** (`src/lab/geomorph-dungeon/`) shares **none** of the engine. It generates *geometry* and bakes content into parallel grids; a room is **not** a config-driven object (see `architecture.md` §4).

**Idea 10 (Room Profile) is literally step 1.** It turns a map room into a config-driven object whose properties (`type`, `material`, `water`, …) are rule-generated and seed its name/description/props — the **same mechanism** `configDungeonGen`'s `roomNameUpdater` already runs (parent Level `type` → Room name), but grounded on the *real* generated map instead of an abstract tree.

## 5. North star / target architecture

- **One shared generation engine, promoted to `core/`** (per the two-zone model, `architecture.md` §1): `core/config` (schema + registry + ordered updater-runner), `core/text` (tracery-lite string templating), `core/rng` (seeded), `core/model` (shared object/tag types).
- **Every generator is a config on the engine** — names, character, dungeon-content, **and the MAP** (its rooms/levels/dungeon modeled as `ItemRecord`s in the tree).
- **The bitmask map becomes the *renderer / view*** of the generated (nested) object tree: **geometry is one facet**, but the generated **semantic object is the source of truth**; naming, descriptions, and props all read from it. Regenerating a property (or re-seeding the tree) updates the map's view.

```
  value pools (weighted+tagged)              ┌─────────────────────────────┐
        │                                    │  generated OBJECT TREE      │
  core/config  ── ordered updaters ─────────▶│  Dungeon                    │
  core/text    ── string templates           │   └ Level (type: cavern) ──┐│
  core/rng     ── seed → reproducible tree    │      └ Room (type,water…)  ││  ← tags flow parent→child
        │                                    │         └ Props / Monsters ││
  configs: names · character · dungeon · MAP └─────────────┬───────────────┘
                                                           │
                                            bitmask map = VISUAL VIEW of the tree
```
